搜歌 Agent v2 · 完整架构设计图

目标：把现有的固定五步 workflow 降级为一个工具，外面加模型驱动的 agent loop。 确定性检索内核（recall / rank / verify / db / index）全部保留，作为 search_songs 的实现。
入口 / 传输 Agent 循环 / LLM 工具 状态 / 记忆 护栏 / 校验 数据 / 外部

00设计原则

模型控制流程
选哪个工具、搜几次、何时澄清、何时结束，都由 LLM 决定；代码只提供工具和边界。
工具少而精
8 个底层工具合并为 6 个面向 agent 的工具；不要把 API 1:1 搬给模型。
状态显式化
会话状态是结构化 JSON，不是聊天原文；上下文主动压缩、工具结果主动清理。
输出可校验
最终曲目必须是工具返回过的 id；非法 id 在代码层拦截，不靠模型自觉。

v1 → v2 的边界变化

环节v1（现状）v2（目标）
多轮动作判定正则匹配“换一首 / 更X / 不要X”LLM 读对话后选择工具
检索流程代码写死五步五步保留，变成 search_songs 的内部
意图解析每次调用 DeepSeek 解析 IntentLLM 在循环里直接产出结构化 filters
推荐理由单独的 LLM 调用LLM 在 finish 时一并写
拒答 / 澄清阈值 + 固定文案工具返回 status + facets，agent 决定说还是问
上下文只存 Intent + seenmessages + state + candidates + 压缩

02Agent 主循环

① 组装上下文 · context_builder
system prompt　+　skill 清单（仅 name/description）　+　session.state　+　最近 N 条消息　+　工具 schema
↓
② LLM 决策 · llm.chat_with_tools()
返回两种结果之一：tool_calls[]　或　最终文本
↓有 tool_calls
③ 工具路由 · registry.run(name, args, ctx)
Pydantic 校验 → 线程池执行（20s）→ ToolResult → 写 trace / calls.jsonl
↓tool_result
④ 回填并压缩 · context.append + compact
只保留高信号字段；大结果存 session.candidates；必要时触发摘要
↺回到 ②，最多 MAX_STEPS=5
⑤ 停止与收尾
finish 工具 / 达到预算 / 超时 → 校验 → 返回 { songs, message, trace }
停止条件（任一命中）
· 调用 finish
· steps >= 5
· searches >= 2
· elapsed > 20s
· tokens > 20k
· 工具连续失败 2 次
每轮写 trace
{step, actor, tool, args, ms, n_items}
供排障、回放、评测复用
成本持平点：单轮明确搜索 = 决策 1 次 + 收尾 1 次 = 2 次 LLM，与 v1 的「解析意图 + 写理由」相同。只有多轮和澄清场景才会多花调用。

03工具面（6 个）

search_songs
query?: str mode?: auto | title | lyric | semantic | similar filters?: Filter # genres/moods/scenes/vocal/languages/duration soft_tags?: str[] exclude_tags?: str[] # 不要伤感 exclude_song_ids?: int[] # 换一首 seed_song_id?: int # mode=similar limit?: int = 30 relax?: bool = false
  • 返回 top-30 紧凑卡片 + facets + confidence + status
  • 内部不调用 LLM，纯确定性；一次调用可完全复现
  • status：ok / empty / refused / low_confidence
refine_candidates
song_ids: int[] drop_tags?: str[] keep_tags?: str[] drop_song_ids?: int[] limit?: int = 5
  • 在已有候选集上做确定性减法，保持原顺序
  • 返回 dropped: {id: 原因}，agent 可直接向用户解释
  • 替代 v1 的 classify_turn("negative")
get_song_detail
song_id: int
  • 返回时长、语种、标签、简介；不含完整歌词（控制 token）
  • 用于“这首歌讲什么 / 多长 / 什么语言”
ask_user
question: str options?: str[]
  • 结束本轮，向前端抛问题；替代硬拒答
  • 例：“没有德语民谣，法语有 6 首，要听吗？”
get_user_profile
limit?: int = 10
  • Top 标签 + 最近常听；user_id 由运行时从 JWT 注入，模型不可填
  • 用于个性化加分，不筛歌
finish
song_ids: int[] # 必须来自工具结果 reasons?: {id: str} message: str
  • 唯一的结构化收尾方式
  • 服务端校验：song_ids ⊆ allowed_ids，否则返回可自纠错误
合并关系：search_by_keyword + filter_by_tags + semantic_search + similar_songs 收敛为 search_songs 的 mode / filters；search_by_lyrics 成为 mode=lyric。 底层函数不删，仍可被工具内部调用。

04search_songs 内部（保留 v1 内核）

① 参数进入
agent 已给出结构化 filters，跳过 intent.parse()；query 只用于语义编码与歌词/title 路
↓
② 按 mode 选路 · recall.py
title：BM25 + fuzzy　·　lyric：LIKE + 词覆盖 + 歌词向量　· semantic：bge-m3 + 标签预过滤　·　similar：向量近邻（排除同歌手）
↓routes / matches / lyric_conf
③ 排序 · rank.py
歌词类直接用置信度；其他类 RRF 融合 → 硬过滤 → 软标签加分 → bge-reranker 重排
↓[(song_id, score)]
④ 校验 · verify.py
点名不在库 / 歌手不匹配 → 直接 status=refused；置信度低 → low_confidence；relax=true 时才自动放宽
↓
⑤ 排除与切片 · exclude_tags / exclude_song_ids
用 db.tag_map 做精确标签匹配，先减后切；保证“不要伤感”是确定性的，不靠模型数数
↓
⑥ 组装返回 · cards + facets
items（≤limit，紧凑字段）　·　facets（moods/genres/languages 计数）　· applied（实际生效的过滤/放宽）　·　confidence　·　status
为什么 facets 很重要：用户问“德语民谣”，返回 0 首，但 facets 告诉 agent “法语 6 首、英语 21 首、德语 0 首”。 agent 可以选择澄清、推荐替代、或如实说没有——而不是被一个固定的拒答文案卡死。

05状态、记忆与压缩

① messages（短期）
最近几轮对话 + 工具调用/结果。会被压缩。
{ role: "user" | "assistant" | "tool",
  content: ...,
  tool_calls: [...],
  tool_call_id: ... }
② state（工作记忆）
结构化、始终注入，约 200 token。
{ goal, constraints,
  rejected_tags, seen_ids,
  last_query, decisions,
  open_questions }
③ candidates（候选池）
最近一次工具返回的完整卡片，不进上下文，按 id 取用。
{ 2148564: { name, artist,
    tags, score, match },
  2311270: {...} }
压缩触发与动作
触发：消息 > 8 轮或 > 12k token
动作：LLM 摘要旧消息 → 写回 state 增量 → 丢弃旧消息 → 保留最近 2 轮原文
原则：优先保留 约束、拒绝项、未解决问题，而不是对话原文
跨会话记忆
已有：user_plays、collect、收藏/播放聚合
新增：user_preference(user_id, tag, polarity, source, updated_at)
写入只来自用户明确表达（“我不喜欢电音”），由 remember_preference 工具落库

06护栏与校验

输入
· JWT → user_id 运行时注入，模型不可填
· 消息长度上限
· session_id 隔离
· 工具参数 Pydantic 校验，错误可自纠
循环
· MAX_STEPS=5
· MAX_SEARCHES=2
· 20s 墙钟 / 20k token
· 工具超时 20s；连续失败 2 次降级
输出
· finish.song_ids ⊆ allowed_ids
· 理由只能引用卡片字段
· 结果不足要说明，不凑数
· 任何异常 → 回退确定性管线

07一次多轮请求的时序

#谁做什么
1User“深夜伤感的歌”
2Loop → LLM决策：search_songs filters={moods:[伤感], scenes:[深夜]} limit=30
3Tool → Loop30 张卡片 + facets + confidence=0.88
4Loop → LLM决策：finish(前 5 首, reasons, message)
5Guard校验 5 个 id 均在工具返回集 → 通过
6Loop → Client{ songs, message }，同时更新 state.seen_ids
7User“不要这么伤感，换点欢快的”
8Loop → LLM决策：refine_candidates(上一轮 30 首, drop_tags=[伤感])
9Tool → Loop剩 11 首 + dropped 原因
10Loop → LLM决策：search_songs(filters={moods:[欢快]}, exclude_song_ids=已展示)
11Loop → LLM决策：finish(5 首, message=“换成更轻快的…”)
12State更新 state.constraints / rejected_tags / seen_ids；必要时压缩 messages
全程没有正则分类。“换一首 / 更X / 不要X / 像这首”都是模型读对话后选择工具与参数。

09关键设计决策

决策原因替代方案（不采用）
搜歌做成 tool，不做成 Skill Skill 是流程知识，本身不执行；执行体必须是可调用工具 把五步写成 SKILL.md 让模型照着做——不可测、不可控
暂时 不用 MCP agent 和工具在同一进程；MCP 是跨宿主协议，只增加边界和成本 一开始就包 MCP server
refine_candidates 做确定性减法 标签匹配、id 运算交给代码；模型会数错、会混淆近义标签 让模型从 30 张卡里自己挑——“不要伤感”不可靠
search_songs 内部 不调 LLM 工具要可复现、可测；意图理解由 agent 在循环里完成 工具内部再调一次 DeepSeek 解析 query——多一跳、不可控
默认返回 top-30 + facets 给 agent 减法空间；facets 让“没有德语但有法语”可被推理 只返回 5 首——没有调整空间；返回 500 首——撑爆上下文
finish 白名单校验 结构上杜绝编造曲库外的歌，不依赖模型自觉 让模型自由输出 JSON
单轮走 快路径 明确查询 2 次 LLM 即可，与 v1 成本持平；多轮才进完整循环 所有请求都跑满 agent loop——贵且慢
