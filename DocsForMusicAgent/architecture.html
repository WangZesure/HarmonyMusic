三条主要请求链路

链路 A首页 / 列表数据
AppHome.ets → Koa/getSwiper

纯读库。推荐那条会先 exec 子进程调 Python，失败则 catch 降级为按 id 取前 N 首。

AVPlayerPlay.ets → GET /stream/{id}Koa → 302 重定向拼 client_id → Jamendo音频 CDN
client_id 只存 .env，不落库、不下发；302 地址里仍可见（公开 API 的固有限制）。

Koa 先把「正在理解 / 正在检索」两条 status 发给客户端，再等 Agent 返回，最后一次性发 result。

02搜歌 Agent 的具体实现

①
意图解析agent/core/intent.py 调 LLM
输入
用户一句话
输出
Intent{}：intents / title / artist / lyric_fragment / filters（硬约束）/ soft_tags / semantic_query / count
DeepSeek JSON 模式 + 代码里按词表校验（模型输出词表外标签会被丢弃）。 歌名短查询走「快速通道」，不调 LLM：0 次调用、约 0.06s。
②
多路召回agent/core/recall.py
输入
Intent
输出
routes{title, lyric, semantic, similar} ＋ matches{ song_id → 命中那句歌词 }
四路并行，每路 top-30。歌词路 = LIKE 命中 ＋ 词覆盖度 ＋ 向量相似度取 max， 再用交叉编码器对 top-15 重排。
③
排序融合agent/core/rank.py 两套逻辑
输入
Intent + routes + matches
输出
[(song_id, score)]
④
校验 / 放宽 / 拒答agent/core/verify.py
输入
Intent + routes + 排序结果
输出
最终结果，或拒答文案
放宽顺序固定：软偏好 → 场景 → 次要情绪 → 流派（最多 2 轮）； 人声 / 语种 / 时长永不放宽。点名的歌或歌手不在库、歌手对不上 → 拒答。
⑤
生成理由agent/core/respond.py 调 LLM
输入
最终前 N 首的歌曲卡片
输出
songs[SongHit + reason]
模型只能从候选 song_id 里挑；歌名、歌手由数据库填 → 结构上不可能编造曲库外的歌。

③ 为什么歌词类要单独走一套

routes四路召回结果
▼
歌词类查询 其他查询
歌词类 · 直接用歌词路线分数
不参与 RRF 融合
不做卡片重排
每首歌取最好的一行，按分数排序
原因：卡片文本里没有那句歌词， 交叉编码器会把正确歌打到第 13–29 名
其他类 · 融合 + 精排
RRF 融合各路结果
元数据硬过滤（人声/语种/时长）
bge-reranker 对歌曲卡片重排
歌名被点名的置顶
