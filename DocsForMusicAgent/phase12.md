## 阶段 1：数据底座（约 8–10 天）

**1.0 先验证可行性（半天，最先做）**
先拿 3 首 Jamendo 歌曲，跑通“拿到地址 → 鸿蒙播放器能播 → 地址隔几天还有效”这条链路。
- 推荐把 Jamendo 的 `tracks/file/?client_id=…&id=…&action=stream` 存进 `url` 字段。这个接口会跳转到真实的音频地址，比 API 直接返回的 `audio` 地址更稳定。
- 要确认的一点是 AVPlayer 会不会跟随这个跳转。如果不跟随，就在 Koa 里加一个 `/stream/:id` 接口做中转。

这一步失败会影响整个音频存储方案，所以放在最前面。

**1.1 拉取候选曲目（1 天）**
- 只要满足以下条件的曲目：允许下载（`audiodownload_allowed=true`）、时长 90–420 秒、带上 `include=lyrics+musicinfo+licenses`。
- 先用 `lang=zh` 把 Jamendo 上能找到的中文歌全部拉下来，数量估计很少，可能只有几十首；然后按情绪标签分批拉英文歌，总共拉 2000 首左右作为候选池。
- 所有响应都缓存到本地，不反复请求，以免耗尽 API 配额。

**1.2 筛选出 500 首（半天）**
- 构成：约 400 首有人声且带歌词的，约 100 首纯音乐（用来回答“学习时听的无歌词音乐”这类请求）。
- 按情绪分层抽样：取 20–25 个主要情绪标签，每个至少 10 首，保证每个标签都能搜出结果。
- 同时清洗歌词：去掉 `[Chorus]`、和弦行、重复空行，过滤掉歌词太短的歌。

**1.3 生成逐句时间轴（3 天，核心技术点）**

每首歌按下面三级顺序处理：
1. 先查 LRCLIB。预计命中率很低，但这一步成本几乎为零；
2. 没命中的，在服务器上下载音频，用 Demucs 分离出人声，再用 stable-ts（large-v3 模型）的 `align()`，把清洗后的歌词逐行对齐到音频上；
3. 对齐置信度太低的，退回用 Whisper 直接转写，并标记为 `asr`。

500 首在单张 GPU 上大约跑 1–2 小时。

建议顺便做一个小对比实验：同一批歌，分离人声后再对齐和直接对齐，各自的误差是多少。这会是简历上一个很实在的数字。

**1.4 LRC 质量检查（1 天）**
- **自动检查**：时间戳必须递增；对齐上的行数占总行数的比例要够高；平均置信度要过阈值；最后一行的时间不能超过歌曲时长。
- **人工抽查**：抽 20 首，边听边看，统计偏差小于 0.5 秒的行的比例，目标 90% 以上。
- 不达标的歌直接剔除，或者用候选池里的歌补位。最后输出一份质量报告。

**1.5 用 DeepSeek 打标签（1 天）**
- 先定一份大约 80 个标签的中文受控词表，分四类：
  - 风格；
  - 情绪：由 Jamendo 的 56 个情绪标签映射过来，例如 energetic 对应“燃/激昂”；
  - 场景：跑步、学习、通勤、雨天、深夜、派对……；
  - 语种和有无人声。
- 调用 `deepseek-chat` 的 JSON 输出模式。输入是歌名、歌手、Jamendo 原始标签和截断后的歌词；输出是从词表里选出的标签、一句中文主题摘要和 3–5 个关键词。
- 用代码校验输出：不在词表里的标签直接丢弃。结果缓存到本地，抽查 30 首。
- 成本估计：500 首 × 约 2.5k Token，大约 125 万 Token，费用在几块钱的量级。

**1.6 入库和客户端适配（1.5 天）**
- 数据库：`songs` 表结构不动，`lyric` 存 LRC 文本，`url` 存流媒体地址，`pic` 存 Jamendo 的封面外链；艺人写入 `singers` 表。
- 新增两张表：
  - `song_meta`：来源 ID、时长、语种、有无人声、快慢、授权链接、LRC 来源和质量分；
  - `song_tags`：每行是 `(song_id, tag_type, tag)`，并建好索引。
- 生成新的种子 SQL，取代现在只有建表语句的 `music.sql`；另外造几个“按情绪划分”的歌单，让首页有内容可以显示。
- 客户端：加一个 `resolveUrl()` 函数，以 `http` 开头的地址直接使用，否则才拼上服务器前缀。替换掉播放器里硬编码的 IP 和那 9 处以上的图片地址拼接。

**1.7 建向量索引（1 天）**
- **歌曲级索引**：把“歌名 + 歌手 + 中英文标签 + 中文摘要 + 前几行歌词”拼成一段文本，用 bge-m3 编码。
- **歌词行级索引**：每两行歌词组成一个窗口，元数据里带上 `song_id` 和这一句的起始时间，用来支持“搜一句歌词，直接跳到这句播放”。
- 500 首歌大约 1.5 万条歌词行，在本机 CPU 上跑十几分钟就够了。Agent 运行时也在本地给用户的问题做编码，每次约 100–300 毫秒，所以向量库直接建在本地，不用从服务器来回拷贝。

**阶段 1 验收标准**
- 500 首歌全部入库，现有 App 的首页、搜索、播放都正常；
- 有人声的歌里，90% 以上有合格的 LRC；
- 两套索引都建好；
- 输出一份数据报告：情绪和语种分布、LRC 来源占比、对齐误差、分离人声前后的对比。

## 阶段 2：工具层（约 5–6 天）

**2.1 搭框架（1 天）**
- 用 FastAPI 和 Pydantic 写，每个工具的参数模型自动生成 OpenAI 格式的 Function Calling schema。DeepSeek 兼容这个格式，直接用 `openai` SDK，把 `base_url` 改成 `https://api.deepseek.com` 即可。
- 工具对数据库只读。统一返回 `{ok, data, error}` 格式，每个工具设置超时，每次调用都记日志，阶段 6 评测要用。

**2.2 工具实现（3 天）**

| 工具 | 实现要点 |
|---|---|
| `search_by_keyword` | MySQL FULLTEXT 加 ngram 分词，按歌名、歌手、专辑匹配；查不到就退回 LIKE |
| `search_by_lyrics` | 全文检索和歌词行向量混合召回，两路结果按排名融合（RRF）；返回命中的那句歌词和时间戳 |
| `filter_by_tags` | 参数的取值用 enum 锁定在词表范围内，防止 LLM 编造标签；支持排除指定歌曲（`exclude_ids`，后面“换一首”要用） |
| `semantic_search` | 歌曲级向量检索，可以先按标签过滤再检索 |
| `similar_songs` | 向量近邻，同时排除同一歌手的歌 |
| `get_user_profile` | 从收藏和播放记录聚合出用户最常听的标签 |
| `recommend_for_user` | 双塔模型：用现有的 `mymusic_data_generator.py` 在新曲库上生成模拟用户行为，然后重新训练；同时提供“对候选结果重排”的模式 |
| `get_song_detail` | 返回给 LLM 的只有摘要信息，不包括 LRC 全文 |

**2.3 工具级评测（1.5 天）**

评测集尽量从数据自动生成，不靠人工逐条写：
- **歌词搜歌**：随机抽 100 句歌词，制造错字、删掉几个字或者只保留半句，看 Top-1 和 Top-5 能不能找回原歌，并对比纯全文检索、纯向量检索、混合检索三种方式；
- **标签过滤**：随机组合 50 组条件，和 SQL 直接查询的结果比对，要求 100% 一致；
- **语义检索**：人工写 30 条中文描述，人工标注结果是否相关，计算 nDCG@5（衡量前 5 个结果的排序质量）。

**阶段 2 验收标准**：所有工具都有单元测试；歌词搜歌混合检索的 Top-5 命中率 90% 以上；命令行里能手动调用每个工具，返回结果正常。

## 风险和应对

- **中文内容几乎没有**：评测集要按曲库的实际内容来设计，不放“周杰伦”这类请求。中文提问靠中文标签和 bge-m3 的跨语言能力来匹配。这一点面试时如实说就行，而且“用中文搜英文歌”本身也是个技术点。
- **服务器可能连不上外网**：那就在本机下载音频，再拷到服务器上做对齐，`04_align.py` 同时支持读本地文件。
- **流媒体地址失效**：1.0 的可行性验证就是为了尽早发现这个问题，备选方案是 Koa 中转接口。
- **Jamendo 歌词质量参差**：1.2 已经有清洗步骤，1.4 还会再过滤一遍；500 首不够的话从候选池里补。
