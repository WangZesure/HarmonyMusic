## 二、设计取舍 / 捷径 · 诚实清单

### A. 算法与检索
1. **歌词全文检索从 `MATCH...AGAINST` 改为 `LIKE`**：本机 MySQL 8.0.19 的 ngram 全文索引会让 `mysqld` 崩溃（`init_search@Item_func_match`，已复现）。代价：召回弱、错字搜不到（全文 Top-5 仅 0.30）。*已记于 CLAUDE.md、phase3_status.md。*
2. **歌词类查询不走卡片重排、也不与语义路融合**，直接用歌词召回顺序：因为卡片文本与歌词对不上，交叉编码器会把正确歌打到第 13–29 名。*已记于 phase3loop.md、phase3_report.md。* （试过"用命中歌词行重排"，更差 0.44/0.68，已弃。）
3. **歌词召回里，`LIKE`/BM25 只吃"原始片段"，生成的英文转述只走向量**：转述的 BM25/LIKE 命中会造出假高分把正确歌挤出前 5。属启发式。*已记于 phase3loop.md。*
4. **【本节新增】意图解析用 JSON 模式 + 代码校验词表，没有用 `phase3.md` 要求的 DeepSeek `strict/enum` 模式**（strict 要 beta 地址且 schema 约束繁琐）。等价效果（词表外标签在代码里被丢弃），但不是"模型物理上无法输出词表外标签"。影响：极端情况下模型可能返回近似标签被丢，而非报错。
5. **【本节新增】BM25 用 `bm25s` + 简化分词**（小写字母数字 + 单个 CJK 字）；中文查询在 BM25 上基本无效，**中文全靠向量兜底**。英文歌名/歌词有效。
6. **【本节新增】RRF 权重、平滑常数 K=60、fuzzy 阈值 0.75、名字/歌手相似度 0.6、重排置信阈值 `RELEVANCE_MIN=0.3` 等，都是经验值，未系统调参**（只有少量 dev 试错，如"去掉 RRF+卡片重排"这一处）。换场景可能需重调。
7. **`bge-reranker` 设 `max_length=256`**（原按模型 8192 做 padding，CPU 慢到不可用）。可能截断超长候选文本。

### B. 评测
8. **评测集偏小**：dev 109 / test 74；无置信区间/显著性检验，"1 条≈1.5 个百分点"。
9. **mood 的 0/1/2 标注不中立**：在 `semantic ∪ agent` 候选池上打的分，两个被评方法都贡献了候选 → 双方都带同源优势（B1 不在池中故偏低）。完全中立需人工标签（`semantic_labels.jsonl` 仍空）。*已记于 phase3_report/phase3loop。*
10. **describe 查询与向量卡片同源**（查询是照卡片摘要生成的），可能高估；另加了 `describe_fuzzy` 缓解但仅 dev 10 条。*已记于 phase3_report。*
11. **constraint 满足集有的很宽**（≥5 起步，个别到 200 首），约束强度不一；靠"gold≥5"规避放宽，不代表真实窄约束下的表现。*已记于 phase3loop。*
12. **消融在 dev 的 36 条分层子集上做**（全量太慢），是相对量级；baseline 在子集上全 1.0（子集偏易）。**且"语言归一"在本子集无差异——等于没在真实带语言条件的查询上单独验证过**。*已记于 phase3_report/phase3loop。*
13. **【本节新增】absent 的"知名歌"是硬编码列表**（周杰伦/Taylor Swift…），覆盖有限；"同名异歌手"靠从库内歌名 × 知名歌手拼。
14. **【本节新增】评测 query 由 DeepSeek 生成**（从卡片生成），自带生成偏差；虽经人工复核删条目，但剩余条目仍可能偏"好答"。

### C. 功能与工程
15. **`recommend_for_user` 未重训双塔**：`phase12 §2.2` 要求在新曲库造合成播放再训练；当前实现退化为"标签偏好推荐 + 候选重排"。*已记于 phase12_report、agent/README。*
16. **长期偏好几乎无输入**：`user_plays` 为空，`get_user_profile` 主要靠 `collects`（也少）。*已记于 phase4_report。*
17. **多轮会话是单进程内存**（无 Redis），重启/多实例会丢；"不要X"（negative）为尽力而为，不保证严格剔除。*已记于 phase4_report。*
18. **客户端 `AiSearch.ets` 未编译/真机验证**（本环境无 DevEco）；SSE 用 `requestInStream`（新 SDK 标注 deprecated）；**语音输入未接**；Agent 服务(:8000)无鉴权、Koa→Agent 无超时重试。*已记于 phase5_report。*（早前"`reason` 为空"是 GBK 测试假象，已更正：见 phase5_report §3。）
19. **Agent 与 Koa 是两个进程**（uvicorn :8000 + node :3000），无统一托管/超时重试。*已记于 phase5_report。*
20. **【本节新增】`HF_HUB_OFFLINE=1`**：为免每次联网校验/超时（本机 C 盘曾满、模型已下到 `resources/hf_cache`）。副作用：换机器/首次部署需先联网下模型或去掉该变量。
21. **【本节新增】放宽机制最多 2 轮**，顺序固定（软偏好→场景→次要情绪→流派），人声/语言/时长不放宽；放宽会牺牲硬约束满足率（这正是 constraint 评测靠"gold≥5"规避的那点）。

### D. 数据
22. **170 首 ASR 歌词不参与歌词检索**（C4），用户搜这些歌的歌词会搜不到。*已记于 phase3_report。*
23. **曲库全英文/纯音乐、无中文歌**（Jamendo 的 `lang` 过滤在本 API 坏掉，拉不到中文）；中文请求靠中文标签 + bge-m3 跨语言匹配。*已记于 phase12_report/phase3_report。*
24. **1 首因单行歌词 >512 字符被整首剔除歌词**（`song_lyric_lines.text` 上限，且明文规定不静默截断）。*已记于 phase12_report/between12。*

## 三、结论：文档是否清楚完整地反映了设计？

- **此前缺口**：算法/工程里有 6 处（4、5、6、7、13、20、21 等）**只写在代码注释里、没进评审文档**——本文档已补齐（标 **【本节新增】**）。
- **未做验证**：语言归一的真实效果、mood/constraint 的全量代表性、客户端的编译与真机——都属"未验证"，非"已通过"。
