## 1. 系统全景与数据流

### 1.1 总图

```
══════════════ 离线：数据流水线（一次性，data_pipeline/00–08） ══════════════
Jamendo API ──01拉候选──02选500首──┬──03 LRCLIB 查同步歌词──┐
                                  │                        ├─05 质检+标准化 LRC──┐
                                  └──04 GPU：Demucs 分离人声 + stable-ts 对齐/ASR ┘     │
                                  ┌─────────── 06 DeepSeek 打标签/中文摘要/语种 ────────┤
                                  ▼                                                    ▼
                          07 生成 seed SQL ──► MySQL mymusic（14 表）      08 bge-m3 编码 ──► 向量索引 data/index/

══════════════ 在线：一次搜歌请求 ══════════════
鸿蒙 App AiSearch.ets
   │  POST /agent/chat {message, sessionId}  + JWT
   ▼
Koa :3000  agentChat（JWT 鉴权 → 转发 → 以 SSE 格式回包）
   │  POST /agent/chat {session_id, query}  + X-User-Id
   ▼
Agent 服务 :8000（FastAPI）
   chat.py 判断本轮是哪种指令 ── session.py 读写会话
      ▼
   pipeline：① intent ─► ② recall ─► ③ rank ─► ④ verify ─► ⑤ respond
                │            │                       │            │
           DeepSeek     8 个工具 / BM25 / 向量索引 / MySQL     DeepSeek
   ▼
返回 {songs[song_id, 名称, 标签, 命中歌词, 理由], message, relaxed, trace}
   ▼
App 渲染卡片 → 用 getSongDetail(id) 回查 pic/url → 点击播放

══════════════ 在线：播放 ══════════════
App AVPlayer ── GET /stream/{id} ──► Koa 302 跳转（client_id 从 .env 拼接）──► Jamendo 音频
```

### 1.2 离线流水线：每一步的输入和输出

| 步骤 | 做什么 | 输入 | 输出 |
|---|---|---|---|
| 00 | 可行性检查：Jamendo 链接能不能播 | client_id | `reports/00_stream_check.json` |
| 01 | 按人声/纯音乐 × 标签拉候选池 | Jamendo API | `candidates.json` |
| 02 | 按情绪分层选 500 首（人声 400、纯音乐 100） | `candidates.json` | `selected.json` |
| 03 | 查 LRCLIB 现成的同步歌词 | `selected.json` | `lyrics.json`（9 首同步，221 首只有纯文本） |
| 04 | GPU 服务器：Demucs 分离人声，stable-ts 按原文逐句对齐；没有歌词文本的走 Whisper 识别 | 音频 + 纯文本歌词 | `lrc/*.lrc`、每行置信度 |
| 05 | LRC 质检和标准化（契约 C4：和原文逐行一一对应、时间戳递增） | `lyrics.json` + `lrc/` | `lyrics_final.json`（来源和是否可检索） |
| 06 | DeepSeek 打标签：流派、情绪、场景（限定在 C3 词表内）、一句中文摘要、语种 | 歌曲元数据 + 歌词 | `tags.json` |
| 07 | 生成种子 SQL 并导入数据库 | 上面全部 | `db/seed_v1.sql`、`lyric_lines.json` |
| 08 | bge-m3 编码，生成两个索引 | 歌曲卡片、歌词行（当前行加下一行） | `index/songs_v1`（500×1024）、`index/lyric_lines_v1`（6823×1024） |

“歌曲卡片”指：歌名、歌手、标签、中文摘要、前几行歌词拼成的一段文本。它既是歌曲向量的编码对象，也是重排模型的输入。

### 1.4 工具层（`agent/tools/`，契约 C7）

统一返回 `{ok, data, error}`，结果为空也算成功；歌曲统一用 `SongHit` 结构表示。

| 工具 | 输入 | 输出 / 实现 |
|---|---|---|
| `search_by_keyword` | 文本 | 歌名、歌手的 LIKE 匹配 |
| `filter_by_tags` | Filter（流派、情绪、场景、人声、语种、时长） | 按 SQL 过滤：同一类标签内任一满足即可，不同类之间必须同时满足 |
| `semantic_search` | 自然语言 + 可选 Filter | 歌曲级向量近邻 |
| `similar_songs` | song_id | 向量近邻，排除同一歌手 |
| `search_by_lyrics` | 歌词片段 | LIKE + 歌词向量，RRF 融合；带回命中的那句和时间戳 |
| `get_song_detail` | song_id | 完整信息 |
| `get_user_profile` | user_id（来自 JWT） | 收藏和播放记录里出现最多的标签 |
| `recommend_for_user` | user_id | 标签偏好推荐（双塔模型没重训，属于降级实现） |

### 1.5 Agent 核心（`agent/core/`）：每个模块的输入和输出

| 模块 | 职责 | 输入 | 输出 | 是否调用 LLM |
|---|---|---|---|---|
| `intent.py` ① | 把用户的话解析成结构化意图。有“快速通道”：短查询且直接包含歌名时，跳过 LLM | query 字符串 | `Intent{intents, title, artist, lyric_fragment, lyric_fragments_en[2–3], filters(硬约束), soft_tags(软偏好), semantic_query, count}`；标签在代码里按词表校验，语种统一成 ISO 代码 | 是，DeepSeek JSON 模式（快速通道除外） |
| `recall.py` ② | 按意图多路召回，每路 top-30 | Intent | `routes{title, lyric, semantic, similar: [song_id]}` + `matches{song_id: 命中的那句歌词}` | 否 |
| `rank.py` ③ | 合并各路结果并排序 | Intent + routes + matches | `[(song_id, score)]`。**歌词类**：直接按歌词路线的分数排序。**其他类**：各路 RRF 融合 → 按数据库元数据硬过滤 → bge-reranker-v2-m3 对歌曲卡片重排 → 歌名被点名的置顶 | 否（用本地重排模型） |
| `verify.py` ④ | 校验、放宽、拒答 | Intent + routes + 排序结果 | 结果不够时按固定顺序放宽（软偏好 → 场景 → 次要情绪 → 流派，最多 2 轮；人声、语种、时长不放宽）；点名的歌或歌手不在库，或歌手对不上时拒答 | 否 |
| `respond.py` ⑤ | 为每首歌写一句推荐理由 | 最终前 N 首的卡片 | `songs[SongHit + reason]`；模型给出的 song_id 不在候选里就丢弃，歌名、歌手由代码填写，**从结构上不可能编造曲库外的歌** | 是 |
| `pipeline.py` | 串起 ①–⑤ | query、要排除的歌、额外软偏好、可选的现成意图 | `{songs, message, relaxed, trace}` | — |
| `chat.py` / `session.py` | 多轮对话 | session_id、query、user_id | 用规则判断本轮属于 4 种指令中的哪种（新查询 / 换一首 / 更 X 一点 / 不要 X），再调用 pipeline，并更新会话 | 只在新查询时调用 |
| `llm.py` | DeepSeek 客户端 | messages | 文本或 JSON；失败重试，按 prompt 哈希做磁盘缓存，统计 token | — |

## 2. 复核：哪些可信，哪些要修

### 2.1 可信的部分

- test 成绩能复现。评测集定稿后没有改过；代码里没有针对评测题的特判（检查过 ID 和查询字符串）。
- “从结构上防编造”成立：模型只能从候选 ID 里挑，歌名由数据库填写。
- 消融结论合理：关掉意图解析后，歌词类和拒答直接崩掉，这和原理一致。歌词类查询必须先识别出“这是歌词”，才会走歌词检索。

### 2.2 固化前必须修（手下的任务单已写进 `phase3loop.md` 末尾）

| # | 问题 | 复现 | 根因 | 改法 |
|---|---|---|---|---|
| F1 | **曲库外的歌词永远不拒答**（10-13 已经指出，被后续的任务单替换掉，一直没修） | 用曲库外的歌词去搜（如“天青色等烟雨”、“we will rock you”、“is this the real life”），都返回 5 首无关歌 | `rank.py` 歌词分支把分数写死成 `1.0 - i*0.01` | 改用 `_lyric_route` 算出的真实分数；用 ≥20 条曲库外歌词定阈值 |
| F2 | **“周杰伦风格的歌”被拒答** | 回复“曲库里没有「周杰伦」这首歌” | 用户提到不在库的歌手，代码一律当成点名查询拒答 | 区分“要这首歌”和“要这种风格”。后者让模型把风格描述出来，再走语义检索，回复说明“曲库没有周杰伦，下面是风格接近的” |
| F3 | **找相似歌，第 1 名是种子歌自己** | “和 Night Train 差不多的歌”，第 1 名是 Night Train | 歌名置顶规则对 similar 意图也生效了 | similar 意图排除种子歌本身 |
| F4 | **歌词类查询的推荐理由全是空的** | “歌词是 I search for the strength”，3 首理由都是空字符串 | `respond.py` 对 `Match` 对象调用 `.get`，抛出的异常被 `except: pass` 吞掉 | 改用 `m.line_text`，并删掉全吞异常的写法 |
| F5 | 我要求的回归测试一条都没加 | `agent/tests` 里只有 10-12 的旧测试和多轮对话测试 | — | 把 F1–F4、Coldplay 的 Yellow、Night Str 写成固定用例 |
| F6 | **ASR 歌词其实能被检索到**，和文档、契约 C4 不一致 | BM25 和 LIKE 读的是整张 `song_lyric_lines`，包括 170 首 ASR 识别的歌（4031 行） | 构建 BM25 时没按“是否可检索”过滤 | 建议过滤掉：ASR 识别的歌词错字多，命中了也不可信。或者明确改契约，二选一 |

### 2.3 说法要更正（属于交代不清，不是造假）

- **“test 只跑一次”不准确**：v1 的 64 条在 10-12 晚上跑过一次，之后改了代码、给 test 追加了 10 条“曲库没有”，又跑了一次。应写成“test 集用过两次，第二次在代码修改之后”。
- **“SSE 流式返回过程”言过其实**：Koa 是在调用 Agent **之前**一口气发出两条“正在理解”“正在检索”的状态消息，真实结果最后一次性返回，状态和实际进度无关。
- **“reason 为空只是 GBK 测试假象”只对了一半**：对描述类成立，但歌词类确实为空（F4）。
- **“长期偏好已实现”**：代码在，但收藏和播放记录都是 0 行，Koa 也没有写播放记录的接口，所以这个功能**从来没有在真实输入下跑过**。

### 2.4 不阻塞、可以排到后面

- **耗时**：没有正式测过。我这边的实测：服务启动后第一条约 45 秒（加载模型），之后单条 1.4–10 秒（会触发放宽的查询最慢），test 集平均约 5 秒一条。原计划要求 P95 ≤ 6 秒，大概率达不到。
- **Koa 转发没有超时**：Agent 卡住时请求会一直挂着。可以用 `fetch(..., {signal: AbortSignal.timeout(20000)})` 解决。
- **双塔推荐没有重训**：App 首页的“AI 推荐”现在走降级方案，返回的是按 ID 排序的前 N 首。
- **git 只有一次初始提交**，所有成果都还没提交。

## 3. 过程中遇到的问题与解决

| 阶段 | 问题 | 根因 | 解决 | 代价 / 遗留 |
|---|---|---|---|---|
| 1 | 找不到同时满足“能合法播放 + 有歌词 + 有逐句时间戳”的开源曲库，中文歌更没有 | 版权限制 | 用 Jamendo（CC 协议，能播），时间戳自己用 GPU 对齐生成 | 曲库是英文独立音乐，大模型基本不认识这些歌 |
| 1 | stable-ts 对齐后会重新断句，41 行歌词输出成 27 行 | 默认按语音重新分段 | 打开 `original_split=True`，05 检查行数和原文一致 | — |
| 1 | 播放链接里带着 Jamendo client_id | 直链里本身就有 | Koa 提供 `/stream/{id}`，302 跳转，client_id 只放 `.env` | 抓包仍能在跳转地址里看到，这是公开 API 的固有问题 |
| 1 | GPU 服务器访问不了 HuggingFace；torch 版本冲突 | 网络限制 | 改用 `hf-mirror.com` 镜像；固定 torch 版本 | — |
| 1 | 170 首人声歌没有歌词文本，只能靠 ASR 识别 | 数据源缺歌词 | ASR 识别的歌词只用于显示，不进歌词检索 | 这部分歌搜歌词搜不到（实际仍被 BM25 检索到，见 F6） |
| 1 | 旧库表结构和新数据冲突；`&amp;` 没转义；字段超长 | 旧表是为 10 首中文歌设计的 | 重写 `schema_v1.sql`；入库前转义；超长直接报错，不静默截断 | 1 首歌因单行歌词太长被去掉歌词 |
| 2 | 只要用全文检索 `MATCH`，MySQL 8.0.19 就崩溃 | 数据库 bug（崩溃日志已确认） | 弃用全文检索，改用 LIKE，阶段 3 再加内存 BM25 | 3 个全文索引成了摆设 |
| 2 | 评测时连接耗尽 | 每次查询都新建连接 | 每个线程复用一条连接 | — |
| 3 | **Agent 输给单次向量检索（0.633 对 0.733）** | ① 模型输出“法语”，数据库存 `fr`，带语言条件的查询全被过滤掉；② 歌词类被卡片语义检索结果稀释，又被不含歌词的卡片重排打乱 | 语种统一成 ISO 代码；歌词类不参与融合和重排，按歌词召回自身的分数排序 | 歌词类和其他类走两套排序逻辑 |
| 3 | “Coldplay 的 Yellow”命中了另一位歌手的同名歌 | 快速通道把歌手丢了 | 快速通道也提取歌手；同时有歌名和歌手时，候选里**没有任何**歌手对得上才拒答 | — |
| 3 | 拼错的歌名“Night Str”被当成曲库没有 | 歌手校验只看第 1 名 | 模糊匹配支持前缀和编辑距离，并限定在该歌手的歌里比较 | 阈值是经验值 |
| 3 | 评测集太简单，满分没有区分度 | 描述类是照着卡片摘要生成的（和向量编码的文本同源）；“曲库没有”只有 5 条 | 补充“曲库没有”到 32 条，恢复条件组合类和氛围类，新增“模糊描述”类 | 氛围类标注用的候选池来自被评测的方法，不完全中立；新增的几类只在 dev 上 |
| 3 | 歌词召回内部做 RRF 后命中率降到 0.08 | **实验本身有 bug**：路由名改了，排序代码读到的是空列表 | 后来改为“每首歌取最好一行、按分数排序” | 当时的结论作废 |
| 3 | 重排模型在 CPU 上极慢 | 默认按 8192 长度补齐 | `max_length=256` | 超长候选会被截断 |
| 5 | curl 测试时推荐理由为空 | Windows 控制台用 GBK 发中文，服务端按 UTF-8 解码出错 | 改用 UTF-8 请求体 | 只解释了描述类，歌词类另有 bug（F4） |

**经验**：这个项目里几次关键突破都来自“逐条追踪正确答案丢在哪一步”，而不是换更强的模型或算法。阶段 3 从 0.633 升到 1.0，靠的是修 4 个实现 bug，没有引入任何新技术。

## 4. 和其他工作的关系，以及技术选型

### 4.1 和 App 原有功能的关系

| 原有功能 | 现在 | 关系 |
|---|---|---|
| 搜索框（LIKE 搜歌名） | 保留；新增“AI 搜歌”页 | 新旧并存。原搜索就是基线 B3，Hit@5 为 0 |
| 首页推荐（双塔模型） | 没改；在新曲库上走降级方案 | Agent 的 `recommend_for_user` 本该复用它，但没有重训（缺播放数据） |
| 歌单 | 按标签自动生成 37 个 | 依赖阶段 1 的标签 |
| 播放器 | 复用，只改了地址解析 `resolveUrl` | 播放走 `/stream/{id}` |
| 歌词显示 | 数据已具备（逐句时间戳） | `Play.ets` 的逐句滚动**不在本次范围**，数据已经可以直接用 |
| 用户 / JWT | 复用 | `user_id` 从 JWT 取，不由客户端传 |

### 4.2 用了哪些技术，为什么

| 技术 | 用在哪 | 为什么用它 | 什么情况下不用它 |
|---|---|---|---|
| **结构化意图解析**（让模型输出 JSON 再由代码校验；RAG 里叫查询改写或自查询） | ① | 消融显示贡献最大：用户的一句话里同时有歌词、语种、风格，必须先拆开 | 只有歌名的短查询走快速通道，不调模型 |
| **BM25**（关键词检索） | 歌名、英文歌词原文 | 精确词命中最可靠，而且便宜 | 中文查询：曲库是英文，BM25 匹配不上 |
| **稠密向量**（bge-m3） | 描述、氛围、中文转述的英文歌词 | 能做语义匹配和跨语言匹配 | 歌名精确匹配：向量会把同义的别的歌也排上来 |
| **RRF 融合** | 多路召回合并 | 不同工具的分数不能直接比较，按名次融合最稳 | **歌词类**：其他路线会稀释歌词路线，实测有害 |
| **交叉编码器重排**（bge-reranker） | 描述类、氛围类 | 查询和歌曲卡片是同一种描述性语言，精排效果好 | 歌词类：卡片里没有那句歌词，排序近乎随机 |
| **元数据硬过滤** | 人声、语种、时长 | 用户明说的条件必须满足，交给数据库判断，比交给模型可靠 | 情绪、场景这类标签是模型打的，有噪声，所以作为可以放宽的条件 |
| **校验、放宽、拒答**（RAG 里叫纠错式 RAG） | ④ | 宁可说“没有”，也不拿不相关的歌凑数 | — |
| **只能从候选里选**（输出受约束） | ⑤ | 结构上保证编造率为 0 | — |
| **固定流水线**（不让模型自己决定下一步） | 整体 | 搜歌的步骤是固定的，固定流水线更可控、更便宜、每一步都能单测 | 见 4.3 |

### 4.3 换个场景，会用别的技术吗？

**先澄清：我们做的算不算 RAG？** 算一半。整条链路是“检索增强”：先检索，再让模型基于检索结果工作。但交付给用户的是**一个排好序的歌曲列表**，不是模型写的一段话。模型只出现在两端：开头理解需求，结尾写理由。结尾“根据检索到的卡片写理由”就是一个很小的 RAG。

| 场景 | 该用什么 | 为什么 |
|---|---|---|
| “这首歌讲的是什么？”“这句歌词什么意思？”“这个歌手什么背景？” | **完整 RAG**：检索歌词、简介，再由模型生成回答，并注明出处 | 答案是一段话，需要模型自身知识以外的事实（这些冷门歌模型不认识），而且必须以检索到的内容为依据。现有的歌词索引可以直接复用 |
| App 使用帮助、版权问答（每首歌都有 `license_url`） | **完整 RAG**，检索文档 | 典型的问答场景，资料多、会更新 |
| 曲库只有几十首 | **直接把整个曲库塞进 prompt**（B1） | 内容放得进上下文时，检索反而是多余的。实测在 500 首时它就不行了：歌词放不进去（歌词类只有 0.125），每条约 5 万 token |
| “帮我建一个跑步歌单，加 10 首，再分享给朋友” | **ReAct**：模型自己决定调用哪个工具、调几次 | 步骤不固定，需要模型规划。消融里那组 ReAct 对照计划要做但还没做；只是搜歌的话，固定流水线就够了 |
| 首页“猜你喜欢”（用户没有输入任何需求） | **推荐模型**（双塔、协同过滤） | 没有查询可以解析，只能靠行为数据。这也是播放记录必须写起来的原因 |
| “和 X 合作过的歌手有哪些” | **知识图谱、GraphRAG** | 关系类查询，向量检索做不好。当前数据里没有合作关系 |
| 复杂的条件统计查询 | **让模型写 SQL**（text-to-SQL），只读、有白名单 | 我们没用，是因为条件组合只有固定几类，用固定 SQL 更安全 |
| 意图解析要求更低延迟、更低成本 | **微调小模型** | 现在每条查询调一次 DeepSeek（约 1–3 秒），用户量大时值得把解析换成本地小模型 |

**判断要不要上 RAG 的四个问题**：
1. 答案是一段话，还是一组条目？是一段话才需要生成。
2. 需要的事实模型自己知道吗？不知道就需要检索。
3. 资料放得进上下文吗？放不进就需要检索。
4. 事实会变吗？会变就需要检索，而不是微调。

本项目的“搜歌”是“一组条目 + 模型不知道 + 放不进上下文”，所以是**检索加排序**，生成只占很小一部分。
