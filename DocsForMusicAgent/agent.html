搜歌 Agent · 数据结构与流水线

固定五步：意图 → 召回 → 排序 → 校验 → 回复。每一步都有明确的输入/输出类型，可单独测试。

01流水线总览

①
意图解析core/intent.py
输入
用户一句话 str
输出
Intent
②
多路召回core/recall.py
输入
Intent
输出
routes + matches + meta
③
排序融合core/rank.py
输入
Intent + routes + matches
输出
ranked: [(song_id, score)]
④
校验 / 放宽 / 拒答core/verify.py
输入
Intent + routes + ranked
输出
放行 / 放宽后重跑 ②③ / 拒答文案
⑤
生成理由core/respond.py
输入
ranked 前 N + matches
输出
[SongHit + reason]
全程还带着一条 trace: list[dict]，每一步追加一条（耗时、条数、top）。评测和线上排障都靠它。

02数据结构

Intent ① 输出
intents从 title / artist / lyric / describe / similar 里选，可多个
title用户点名的歌名，没有则 null
artist点名的歌手
lyric_fragment引用的歌词原文（中英皆可）
lyric_fragments_en中文歌词的 2–3 种英文转述，走向量匹配
filtersFilter：硬约束，只在用户明说时填
soft_tags软偏好，只加分不筛除
semantic_query改写成"歌曲卡片"风格的描述，给向量检索
count要几首，默认 5
硬约束 vs 软偏好是这个结构的核心区分：前者由数据库强制执行，后者可以放宽。
Filter Intent.filters
genres流派，值来自契约 C3 词表（23 个）
moods情绪（20 个）
scenes场景（17 个）
vocal"vocal" / "instrumental" / null
languagesISO 639-1 两字母码（fr / de / zxx）
duration_s{min, max} 秒
模型输出的"法语"会在代码里归一到 fr —— 否则和库里存的 ISO 码对不上。
routes / matches / meta ② 输出
routes{路线名: [song_id, …]}，四路：title / lyric / semantic / similar，每路 top-30
matches{song_id: Match}，只对歌词路线有值
meta.lyric_conf{song_id: 置信度}，歌词"像不像用户引的那句"
meta.similar_seed相似歌查询的种子 song_id
matches 是歌词类独有的结构 —— 它记住"命中在第几行、那句话、第几毫秒"。
Match matches 的值
typekeyword / lyric / tag / semantic / similar / cf
line_no命中的是第几行歌词（从 0 开始）
line_text那句话的原文
start_ms这句在歌里的起始毫秒 —— 前端可以直接跳到这里播
非歌词路线的 Match 只有 type，其余字段为 null。
SongHit ⑤ 输出
song_id · name · artist标识
duration_s · vocal · language来自 song_meta
genres · moods · scenes来自 song_tags
rank · score名次与分数
match命中的证据（歌词行 / 关键词 / 语义）
reasonLLM 写的一句推荐理由（只能基于上面的字段）
刻意不含 lyric / url / pic —— 喂给模型的内容控制在必要字段， 避免超长和无关信息。
trace 贯穿全程
stepintent / recall / rank / relax / gray / lyric_source / respond
…每步自带的字段（耗时才、条数、top、放宽描述）
线上出问题时，一次请求的 trace 就能看出"答案丢在哪一步"—— diagnose_stages.py 就是批量吃这个结构。

03一个完整例子（真实 trace）

用户输入："有首歌歌词是 I search for the strength"
1
意图解析 → Intent
{
  "intents": ["lyric"],                     // 判定为「按歌词找歌」
  "lyric_fragment": "I search for the strength",
  "lyric_fragments_en": [],                  // 原文是英文，不需要转述
  "filters": { "genres": [], "moods": [], "scenes": [],
               "vocal": null, "languages": [], "duration_s": null },
  "soft_tags": ["励志", "希望"],            // 模型推测，只加分
  "semantic_query": "一首关于寻找力量与希望的歌…",
  "count": 5
}
用户没给任何硬约束，所以 filters 全空；「励志/希望」是模型推断的软偏好。
2
多路召回 → routes + matches
// routes：每路一条候选列表
{ "lyric": [62 个 song_id], "semantic": [20 个 song_id] }

// matches：只有歌词路线有值，记录"命中在哪一行"
{
  2148564: Match(line_no=7,
                 line_text="I search for the strength",
                 start_ms=32280),
  2311270: Match(line_no=6,
                 line_text="I am a lighthouse keeper, I search for the mast",
                 start_ms=26720)
}
歌词路线 62 条：LIKE 命中 + 词覆盖度 + 歌词向量，三者取 max。 semantic 20 条是卡片语义的补充。
3
排序 → ranked
[(2148564, 1.000),   // 整句原样命中 → 满分
 (2311270, 0.800),   // 命中后半句
 (2264038, 0.731),   // 语义相近的另一句
 … 共 30 条 ]
歌词类不走 RRF 融合、也不走卡片重排，直接用歌词路线的分数排序。 原因：卡片文本里没有那句歌词，交叉编码器会把正确歌打到第 13–29 名。
4
校验 → 通过，不放宽不拒答
top score = 1.000  ≥  LYRIC_MIN_CONF 0.75   // 置信度闸门
relaxed = []      // 没有触发放宽
refuse  = null   // 没有拒答
闸门的作用：判断"用户引的这句歌词，我们到底认不认得"。 低于阈值就拒答「不太确定你想找的是哪首」，而不是拿不相关的歌凑数。
5
生成理由 → SongHit
{
  "song_id": 2148564,
  "name": "A Road in the Country",
  "artist": "Caleb Lemond",
  "duration_s": 203, "vocal": "vocal", "language": "en",
  "genres": ["乡村", "民谣"],
  "moods": ["希望", "平静", "怀旧"],
  "scenes": ["散步", "旅行", "深夜"],
  "rank": 1, "score": 1.0,
  "match": { "type": "lyric", "line_no": 7,
             "line_text": "I search for the strength",
             "start_ms": 32280 },
  "reason": "歌词唱出“I search for the strength”，在乡村民谣的平静氛围中传递寻找力量与希望的心境。"
}
模型只能从候选 song_id 里挑；歌名、歌手、标签全部由数据库填 —— 结构上不可能编造曲库外的歌。
这条链路的三个可验证点：① 每一跳都有明确类型，可以单独断言； ② matches 保留了"证据"（第 7 行、32.28 秒），前端能直接跳转； ③ trace 记录了每步耗时与条数，出问题能定位到具体一步。

04结构上的分叉：歌词类 vs 其他

歌词类 · 直接用歌词分数
• 不参与 RRF 融合
• 不走卡片重排
• 每首歌取最好的一行，按分数排
原因：卡片文本里没有那句歌词，交叉编码器会把正确歌打到第 13–29 名。
其他类 · 融合 + 精排
• RRF 融合各路结果
• 元数据硬过滤（人声/语种/时长）
• bge-reranker 对卡片重排
• 歌名被点名的置顶
例：「深夜伤感的歌」→ semantic 20 条 → 重排 → top 0.729。

05失败路径同样是结构

情况返回结构
点名的歌/歌手不在库 songs = []，message = "曲库里没有《Yellow》…"， trace 里 step="intent" 后直接结束
歌词置信度不够 songs = []，message = "不太确定你想找的是哪首，能再具体描述一下吗？"
结果不够，触发放宽 relaxed = ["放宽场景", "放宽流派"]， 重跑 ②③ 后返回；回复前缀「（放宽了：…）」
完全无结果 songs = []，message = "没有找到符合的歌，换个说法或放宽条件试试？"
真实反例："求一首深夜伤感的德语民谣" —— filters 要求 民谣 + 伤感 + 深夜 + 德语， 语义召回 0 条，放宽软偏好（0）、放宽场景（0）后仍然为空。 这类"窄约束 + 冷门语种"就是拒答的典型场景。
