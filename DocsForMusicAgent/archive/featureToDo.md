先说结论：建议把搜歌 Agent 做成一个**独立的 Python 服务**，部署在现有的 Koa 后端旁边。现有的搜索和双塔推荐都包装成它可以调用的“工具”，然后按“先定评测 → 补数据 → 做工具 → 做 Agent → 接入 App → 评测迭代”六个阶段推进。最大的风险不在 Agent 本身，在数据：现在的曲库没法支撑“按情绪/场景搜歌”。

## 现状：看过代码后的几个关键事实

- **搜索很原始**：`openKoa/controller/api.js` 里的 `searchSong` 只对歌名、歌手名、歌单标题做 `LIKE '%关键词%'`，默认每页 3 条。“下雨天听的伤感粤语歌”这种话完全搜不到。
- **歌曲表没有语义字段**：`songs` 表只有 `name / introduction / lyric / singer_id / pic / url`，没有语种、风格、情绪、年代这些标签。只有 `song_lists` 有一个 `style` 字段。
- **仓库里没有歌曲数据**：`music.sql` 只有建表语句，没有 INSERT；`recommend/data/` 是空的。推荐服务目前是 Koa 用 `exec` 调起 `python scripts/api/simple_recommend.py`。
- **客户端可以直接复用**：已有 `Search1.ets` / `SearchList.ets` 搜索页、`SongItem` 歌曲卡片、`PlayService` 播放器，以及语音识别相关代码（`AudioCapturer.ts`、`AsrConstants.ts`）。

## 阶段规划

**阶段 0：先定目标和评测集（1–2 天）**
写清楚 Agent 要支持哪几类请求，比如：
- 精确搜索：“周杰伦的晴天”
- 模糊描述：“很燃的跑步歌”
- 歌词片段：“窗外的麻雀在电线杆上多嘴”
- 结合个人偏好：“推荐点我会喜欢的”
- 多轮修改：“换一首更欢快的”

然后人工写 50–100 条测试问题，每条标上“哪些歌算对”。这一步决定了你最后简历上能写出什么数字：Agent 和原来的 LIKE 搜索比，Hit@5（前 5 条里有没有命中）、任务成功率、平均延迟各是多少。

**阶段 1：数据底座（最关键，3–5 天）**
- **补曲库**：至少需要几百到几千首带歌词的真实歌曲。可以用公开数据集，或者从音乐平台抓元数据（只要歌名、歌手、歌词、简介，不碰音频版权）。
- **用 LLM 离线打标签**：给每首歌生成语种、风格、情绪、适用场景、年代，写进新增字段或一张标签表。
- **向量化**：把“歌名 + 歌手 + 标签 + 歌词摘要”做成 embedding，存进向量库。规模小的话，Chroma 甚至 numpy 都够用。

**阶段 2：工具层（2–3 天）**
把能力包装成带 JSON Schema 描述的工具，每个工具单独测试：
- `keyword_search`：复用现有 LIKE 搜索，并扩展到歌词
- `filter_by_tags`：按结构化标签过滤
- `semantic_search`：向量语义检索
- `get_user_recommend`：调用现有双塔模型
- `get_user_profile`：读取收藏和历史，作为偏好
- `get_song_detail`：查歌曲详情

**阶段 3：Agent 核心（单轮，4–6 天）**
建议自己用 Function Calling 手写调用循环，不急着上 LangGraph。原因是面试时能讲清楚每一步。流程是：
1. 意图解析：把用户的话输出成结构化约束，例如 `{语种: 粤语, 情绪: 伤感, 场景: 雨天}`；
2. 选择和调用工具：可以多路并行召回；
3. 合并、去重、重排；
4. 结果为空或太少时自动放宽条件，比如去掉年代限制；
5. 返回歌曲列表，每首附一句推荐理由。

服务用 FastAPI 写，放在 `recommend/` 旁边，比如新建 `agent/` 目录。这样还能顺手把现在 `exec` 子进程调用 Python 的方式换成 HTTP 调用。

**阶段 4：多轮对话与记忆（3–4 天）**
- **会话状态**：记录当前的约束条件和已经推荐过的歌。“换一首”就是排除已推荐的；“更欢快一点”就是修改情绪约束后重新检索。
- **长期偏好**：从收藏和播放记录里提取，作为排序时的加权。

**阶段 5：接入 App（3–5 天）**
- **Koa**：新增 `/agent/chat` 接口，鉴权复用现有 JWT 中间件，用 SSE 流式返回“正在理解 → 正在检索 → 结果”这几个过程。
- **鸿蒙端**：新增一个“AI 搜歌”对话页面，结果直接用 `SongItem` 卡片展示，点击就能用 `PlayService` 播放；输入框接上已有的语音识别。

**阶段 6：评测、消融和收尾（2–3 天）**
- 用阶段 0 的评测集跑三组对比：原 LIKE 搜索、只有向量检索、完整 Agent。再做两个消融：去掉放宽机制、去掉偏好加权。同时记录 Token 消耗和延迟。
- 整理 README 和演示视频，最后把数字填进简历。
