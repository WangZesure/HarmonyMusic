# 阶段 3：Agent 核心（单轮搜歌）

> 前置：阶段 1、2 已验收（见 `phase12_report.md`）。接口遵守 `contracts_v1.md`（C3 词表、C7 工具）。
> 范围：**单轮**。多轮记忆、换一首属于阶段 4；Koa/SSE/客户端属于阶段 5。

## 0. 目标与基线

目标：同一批查询上，Agent 的命中率明显高于“把需求丢给大模型直接猜歌名”，且**不编造曲库里没有的歌**。

曲库是 500 首 Jamendo 独立音乐，大模型几乎不认识，直接猜的命中率接近 0，赢它不说明问题。所以必须同时和更强的基线比：

| 编号 | 方法 | 说明 |
|---|---|---|
| B0 | 大模型直接猜 | 只给用户需求，输出歌名，再到曲库里模糊匹配 |
| B1 | 整个曲库塞进上下文 | 500 首的歌名、歌手、标签、中文摘要全部放进 prompt（约 4–6 万 token），让模型挑。**这是最该赢的基线** |
| B2 | 单次向量检索 | 只调 `semantic_search`，不做解析、不重排 |
| B3 | 原 App 搜索 | 原 Koa 的 `LIKE` 搜索 |
| A | 本阶段 Agent | 第 2 节的流水线 |

Agent 要赢 B1 才说明检索有价值；同时记录每条查询的 token 和耗时，B1 很贵，这本身也是结论。

## 1. 先做评测集（3.0，最先做）

评测集定下来之前不写 Agent 代码，否则改进没法衡量。

文件：`agent/eval/golden_dev.jsonl`、`golden_test.jsonl`，各约 100 条。只在 dev 上调参，test 只在最后跑一次。

| 类型 | 占比 | 示例 | 标准答案 | 指标 |
|---|---|---|---|---|
| 指定歌曲（歌名/歌手，含拼错） | 15% | “放一下 night trian” | 1 首 | Hit@1 |
| 歌词片段：原文、记错、**中文转述英文歌词** | 25% | “有句歌词大概是说火车在夜里开” | 1 首 | Hit@1 / Hit@5 / MRR |
| 描述找歌：不给歌名，描述某首歌 | 20% | “一首法语说唱，有点丧” | 1 首 | Hit@5 / MRR |
| 氛围/场景 | 20% | “下雨天看书听的” | 多首，分 0/1/2 级相关 | nDCG@5 |
| 硬约束组合 | 15% | “3 分钟以内、纯音乐、钢琴、安静” | 用 SQL 算出满足条件的全集 | 约束满足率@5 |
| 曲库没有 | 5% | “来首周杰伦的晴天” | 无 | 正确拒答率、编造率 |

构造方法：
- **指定歌曲、歌词、描述类**：随机抽目标歌，把歌曲卡片（歌名、标签、摘要、歌词）给 DeepSeek，让它模拟用户写查询，要求不能抄歌名。这样每条查询自带标准答案。
- **硬约束类**：由脚本组合约束条件，用 SQL 算出满足条件的歌曲集合作为标准答案。
- **氛围类**：用工具召回 top-20 候选，DeepSeek 按 0/1/2 打分，人工抽 20 条复核。这一步顺带补上阶段 2 缺的语义检索 nDCG 标注。
- **人工把关**：人工过一遍全部 200 条，删掉含糊不清或答案不唯一的。

每条字段：`{id, type, query, gold_ids, graded:{id:0|1|2}, constraints, split}`。另外给 50 条标注期望的解析结果（第 2.1 节的 `Intent`），用来单独评测解析准确率。

**3.0 交付**：评测集 + `agent/eval/run_eval.py` + B0–B3 四个基线的成绩表。

## 2. Agent 流水线

整体是**先规划再执行的固定流水线**，不做让模型自由决定下一步的循环。原因：搜歌的步骤基本固定，固定流水线可控、便宜、好调试，每一步都能单独测。让模型自由调用工具的 ReAct 版本作为第 4 节的对照实验。

```
用户输入
 → ① 解析意图（LLM，结构化输出）
 → ② 按意图多路召回（并行，无 LLM）
 → ③ 融合 + 硬约束过滤 + 重排
 → ④ 校验与放宽（不够数就放宽条件重搜，最多 2 轮）
 → ⑤ 生成回复（LLM，只能引用候选里的歌）
```

### 2.1 解析意图（对应 RAG 里的查询改写和自查询）

用 DeepSeek 函数调用，一次输出：

```json
{
  "intents": ["lyric", "describe"],
  "title": null, "artist": null,
  "lyric_fragment": "火车在夜里开",
  "lyric_fragment_en": "train in the night",
  "filters": {"moods": ["伤感"], "vocal": "vocal", "languages": [], "duration_s": null},
  "soft_tags": ["孤独"],
  "semantic_query": "一首关于夜行列车、孤独伤感的独立民谣",
  "count": 5
}
```

要点：
- **标签用枚举**：schema 里的标签字段是 C3 词表的 enum，开 `strict` 模式（需要 beta 地址，见下方 DeepSeek 说明），模型就无法输出词表外的标签。别名表（“emo→伤感”）写进 system prompt。
- **区分硬约束和软偏好**：用户明说的（“纯音乐”“3 分钟内”）放进 `filters`，是硬约束；模型推测的放进 `soft_tags`，只用来加分。这是避免放宽条件时误伤用户原意的关键。
- **跨语言**：曲库歌词大多是英文，用户用中文转述时，额外生成英文版 `lyric_fragment_en`，两种都拿去检索。
- **改写语义查询**：`semantic_query` 改写成和歌曲卡片同一种写法（歌曲向量就是用卡片文本算的），提高向量匹配度，属于 HyDE 的简化版。
- **简单查询走快速通道**：明显只是歌名或歌手的短查询，先用规则加关键词检索，直接命中就跳过 LLM，省一次调用。

### 2.2 多路召回

每种意图对应一路召回，并行执行，每路取 top-30：

| 意图 | 召回方式 |
|---|---|
| title / artist | 关键词检索（**新增 BM25**，见下） |
| lyric | `search_by_lyrics`：中文、英文两版各查一次 |
| describe / mood / scene | `semantic_search`，用 `filters` 预过滤 |
| similar（“像 X 那样的”） | 先用关键词检索找到 X，再调 `similar_songs` |

**工具层要补的**：
- **BM25 替代 LIKE**：现在 MySQL 全文索引会崩，`LIKE` 的 Top-5 只有 0.30，且一个错字就搜不到。在内存里给歌名、歌手、歌词行建 BM25 索引（`bm25s` 库，1 万行，毫秒级），并做大小写和标点归一化。
- **歌曲卡片**：`songs_v1` 已经把歌名、标签、摘要和前几行歌词拼在一起再编码，这一步已经做了，不用改。

### 2.3 融合与重排

1. **融合**：各路结果按排名做加权 RRF（C7 约定不同工具的分数不能直接比）。权重在 dev 集上调。
2. **硬约束过滤**：不满足 `filters` 的直接剔除，用数据库元数据判断，不靠模型。
3. **重排**：融合后的前 30 首交给交叉编码器 `BAAI/bge-reranker-v2-m3` 重排（多语言，和 bge-m3 同一家，本地 GPU 或 CPU 都能跑 30 条）。查询用原始输入，候选用歌曲卡片。歌词类查询的候选文本换成命中的那句歌词加歌名。业界经验是：重排是单项收益最大的改动。
4. **软偏好加分**：命中 `soft_tags` 的小幅加分。

### 2.4 校验与放宽（对应纠错式 RAG，即 CRAG）

- **校验**：满足硬约束、且重排分数高于阈值的歌不足 `count` 首时，触发放宽。
- **放宽顺序固定**：先去掉 `soft_tags`，再去场景，再去次要情绪，最后去流派。**用户明说的人声/纯音乐、语言、时长不放宽。** 最多 2 轮。
- **说明放宽了什么**：每次放宽都记下来，回复里要告诉用户，比如“没有找到同时满足 A 和 B 的，下面是满足 A 的”。
- **拒答**：
  - 用户点名的歌名或歌手在曲库查不到（关键词检索得分低于阈值），就明确说“曲库里没有”，再给最接近的替代；
  - 重排最高分都低于阈值时，也要说明“不太确定”。
  - 不能拿不相关的歌凑数。

### 2.5 生成回复

- 把最终候选的歌曲卡片交给 DeepSeek，让它为每首写一句推荐理由，只能引用卡片里的事实（标签、命中的歌词行、时长）。
- **从结构上防止编造**：输出格式为 `[{song_id, reason}]`，代码检查每个 `song_id` 都在候选集合里，不在的直接丢弃；歌名、歌手由代码从数据库补，不让模型写。所以编造率按结构就应该是 0，评测时也要统计验证。
- 返回结构：`{songs: SongHit[] + reason, message, relaxed: [...], trace: [...]}`。`trace` 记录每一步的输入输出和耗时，阶段 6 写报告要用。

### 2.6 DeepSeek 使用注意

- 现在的主力模型是 V4 系列（`deepseek-v4-flash` / `pro`）。旧名 `deepseek-chat` 写在 `.env`，模型名不要写死在代码里。
- 用 `tool_choice` 强制调用某个工具时，必须关闭思考模式（`"thinking": {"type": "disabled"}`），否则会返回 HTTP 400。
- `strict` 模式要用 `https://api.deepseek.com/beta`；schema 中每个对象的所有字段都要列为 required，并加 `additionalProperties: false`，可空字段用 `anyOf` 加 `null` 表示。
- 解析和生成的 temperature 设低（0–0.3），保证评测结果可复现；LLM 响应按 prompt 哈希做磁盘缓存，重复跑评测不重复花钱。

## 3. 代码结构

```
agent/
├── core/
│   ├── intent.py      ① 解析 + Intent 模型（pydantic）+ 快速通道
│   ├── recall.py      ② 多路并行召回
│   ├── rank.py        ③ RRF + 硬约束过滤 + reranker
│   ├── verify.py      ④ 校验 / 放宽 / 拒答
│   ├── respond.py     ⑤ 回复生成 + id 校验
│   ├── pipeline.py    串起①–⑤，产出 trace
│   └── llm.py         DeepSeek 客户端（重试、缓存、token 统计）
├── tools/bm25.py      新增 BM25 关键词检索（替代 LIKE）
├── eval/golden_*.jsonl  run_eval.py  baselines.py
└── app.py             新增 POST /agent/search（非流式；SSE 放到阶段 5）
```

不引入 LangGraph 之类的框架，保持原计划自己写，每一步都是普通函数，便于单测和消融。

## 4. 消融实验（3.5，为阶段 6 准备）

在 test 集上每次只关掉一个模块，看指标掉多少：

- 去掉意图解析：原句直接做向量检索，即 B2；
- 去掉 BM25：退回 `LIKE`；
- 去掉 reranker；
- 去掉中文转英文的跨语言歌词检索；
- 去掉放宽逻辑；
- 固定流水线换成 ReAct：把 8 个工具全给模型，自由调用，最多 5 步。

| 步骤 | 内容 | 验收 |

| 指标 | 目标 |

## 6. 顺手修的阶段 2 小问题

- `eval_tools.py` 里三种方法共用一个随机数生成器，所以每种方法拿到的扰动查询不一样，对比不公平。改为先生成好查询，再给三种方法用。
- 阶段 2 的歌词评测用的都是原句的轻微扰动，结果偏乐观（0.94）。3.0 的评测集加了记错和中文转述，以那个结果为准。
- 170 首 ASR 歌词不参与检索（C4），所以用户搜这些歌的歌词会搜不到。评测集的歌词类只从 201 首可检索的歌里抽，报告里写明这一限制。
