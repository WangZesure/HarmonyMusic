一个 Agent，从最简架构开始

先把 OpenAI 那份文档里的原型缩到不能再小：Model + Tools + Instructions + Guardrails， 跑在一个 Run 循环里。然后沿着一次真实请求，看这四件东西和这个循环，分别落在我们仓库的哪里。 下文里的“定义 / 实例 / insight”，指的都是同一件事的三个面：它是什么、我们怎么写、以及为什么这样写。

① 最简架构 ② 循环与状态（动画） ③ 四个部件 ④ 上下文工程 ⑤ 边界与真实链路 ⑥ 收束

01最简架构：四件东西，一个循环

这不是我们的发明。OpenAI 的《A Practical Guide to Building Agents》把单 agent 拆成 Model、Tools、Instructions、Guardrails 四件东西，外面套一个 Run：模型决定下一步， 工具执行，结果回到模型，直到模型给出最终输出或触发退出条件。

Run 不是第五个部件，它是“谁来选下一步”这件事本身。四件东西在框里；框外的 Fast Path 是确定性例外。 Instructions 是随每次请求一起交给模型的文字；Guardrails 在工具边界和 finish 出口复核。
输入/输出 Model Tools Instructions Guardrails

四件东西各一句话：Model 决定下一步；Tools 执行并把结果带回来； Instructions 规定什么时候用哪个工具；Guardrails 在模型说错时仍然生效。 Run 负责把它们串起来，并在该停的时候停。

Baseline · 同一批工具，固定顺序

Pipeline：下一步写死在代码里

仓库里确实有这条路径（agent/core/pipeline.py，旧的 /agent/search 还在用它）：

intent → recall → rank → verify → respond

它也能搜歌。区别是：代码知道下一步是什么。模型只在“解析意图”和“生成理由”两格出现， 中间的顺序、次数、分支都是人写死的。遇到“先不要伤感、再换一批、顺便解释第二首”这种组合， 你得提前把所有分支写出来。

Agent · 同一条链路，顺序交给模型

Run：每一步由模型选，边界由代码守

同一个问题，在 Agent 里变成：模型看到工具清单和会话笔记，自己决定先搜、再筛、还是问用户。 循环只做四件事：调用、执行、回填、检查退出。

model → tool → result → model → … → finish / ask_user

代价是模型可能选错；收益是没人写过的组合也能走通。所以 Agent 的工程量不在“循环”， 在工具契约、规则、边界和上下文——也就是后面四节。

为什么“不要伤感”不是简单删一条约束？ 被 refine 掉的歌如果还留在允许收尾的集合里，模型就能在 finish 里把它塞回结果—— 所以 refine 成功后，循环只允许收尾剩下的歌。如果用户是在新的一轮说“不要伤感”， 就重新召回并带上排除条件，而不是复用上一轮的候选（唯一例外是澄清回答轮， 而且候选必须来自提问那一轮）。

03四个部件、一个循环和它的两端

每一块只回答三个问题：它是什么（定义）、我们把它写在哪（实例）、以及这个选择换来了什么（insight）。

前四张是 OpenAI 原型的四件东西；Run 是循环本身，Input/Output 是循环的入口和出口—— 它们不是第五、第六个部件。

Model

决定下一步的那一个
给定消息和工具清单，输出“调用哪个工具、参数是什么”，或者一个最终回答。
实例：agent/core/llm.py 里的 OpenAI 兼容客户端，指向 DeepSeek；温度 0， tool_choice=auto；单次 30s，Run 的 45s 截止之前最多 3 次尝试。
insight · 模型不需要知道曲库。它只需要知道有哪些工具、每个工具吃什么。 换一个模型，这层以外的代码不用动。

Instructions

数据里没有的行为规则
告诉模型：什么时候搜、什么时候在候选上做减法、什么时候问用户、什么时候必须收尾。
实例：agent/prompts/system.md 的规则 1–9 + 标签白名单（C3 词表）。比如“换一首”→ exclude_song_ids=seen；“不要X”→本轮 refine 或新一轮重搜； 有歌→必须 finish；表外标签→ask_user。
insight · 规则必须和工具现实一致。这一轮把跨轮复用收紧成一条例外： 只有澄清回答轮、且候选来自提问那一轮，才允许复用；其余一律重搜。一条工具会拒绝的规则， 比没有规则更糟：模型会照着做，然后卡在错误里。

Tools

带 schema、超时和结果契约的动作
每个工具只做一件确定的事，返回结构化结果；模型只能通过这些结果看世界。
实例：agent/tools/agent_tools.py 的 7 个工具。 search_songs 返回卡片 + facets + applied filters； refine_candidates 返回 kept_ids / dropped； finish 与 ask_user 是两个出口。
insight · 工具边界决定模型能错在哪里。集合减法、约束复核、id 白名单 都放进工具或服务端；prompt 只负责“何时用”，不负责“怎么做”。

Guardrails

模型说错话时仍然成立的检查
不依赖模型自觉的硬约束：能做什么、最多做几次、结果必须满足什么。
实例：finish 的 allowed_ids 白名单与 satisfies(filters) 复核；标签/语种归一或拒绝；5 步、2 次搜索、45s、20k tokens；会话锁与 turn_id 幂等；失败时返回 degraded{reasons, at_step, partial}。
insight · 不要相信模型声称的 id 合法。在边界上验证，并且无论发生什么， 都返回一个客户端能渲染的结果。

Run

循环本身
调用模型、执行工具、把结果喂回去；在 finish / ask_user / 无工具调用 / 超限 / 异常时退出。
实例：agent/core/agent_loop.py · run()。每一步写一条 trace； 客户端断开时停止并把这一轮的状态丢掉，不写回会话；同一 turn_id 的重试直接返回上次结果。
insight · 循环特意做得很笨。它不做决定，只拥有边界、记录和收尾。 真正的智能在模型和工具里，真正的安全在 Guardrails 里。

Input / Output

上下文与契约
输入是“模型被允许知道的”；输出是“客户端能渲染的”。两者都是结构化契约，不是随手拼接的字符串。
实例：输入 = system.md（Instructions）+ 当前消息 + SESSION NOTES（constraints / rejected_tags / seen / last_shown / last_search / pending_question / summary）+ 最近 6 条消息（约 3 轮）；输出 = type ∈ songs / clarify / refusal / text + degraded + trace。
insight · 上下文是被组装的，不是被积累的。这直接决定了下一节： 为什么状态长这样，而不是把整段聊天记录丢进去。

04上下文工程：为什么模型看到的是这些

上下文就是模型这一次请求能看到的全部文字：系统提示、会话笔记、最近对话、用户这句话、 工具结果。它们共享一个固定大小的窗口。Anthropic 的《Effective Context Engineering》 把这套安排叫上下文工程，并指出窗口塞得越满，模型越容易漏掉指令——context rot。

Instructionssystem.md：规则 1–9、标签词表、示例
SESSION NOTES结构化笔记：约束、已展示、候选、待答问题
Recent最近 6 条消息（约 3 轮；落库 8 条）
User当前这句话
Tool results卡片、facets、详情；按需取
一次请求真正进模型的上下文。没有全量歌词，没有 500 首歌的清单，也没有完整历史。
第一轮 · 模型决定之前

只带这次决策需要的东西

system.md + 笔记 + 最近 6 条消息（约 3 轮）+ 当前这句话。搜索只返回紧凑卡片，不返回歌词； 用户追问时再调 song_detail（JIT）。工具返回的完整 payload （facets、歌词、完整字段）只活在当前轮的 messages 里，超长时从尾部丢弃 （compaction / tool result clearing）；跨轮只留一份最多 60 张的紧凑候选摘要。

system.md + notes + recent[-6:] + query → model → 工具返回：卡片 / facets / matched line
这一轮结束 · 下一轮开始前

只把结论留给下一轮

约束、seen、last_shown、最多 60 张紧凑候选卡片写进 MySQL 的 state_json；原始工具 JSON、歌词全文不跨轮保存。 下一轮开头再把这份笔记注入一次（structured notes），候选只带前 10 张。

state → constraints / seen / last_shown / last_search → agent_sessions.state_json（30 min TTL）

四招——按需取（JIT）、压缩（compaction）、清结果（clearing）、写笔记（notes）—— 不是四个步骤，而是同一个原则：每一轮只放“这次决策真正需要的”。另一种常见的 baseline （不是第一节那条 pipeline）是把所有候选的完整字段、全部历史、能拿到的歌词都塞进 prompt； 在 500 首的曲库里还能跑，再大一点模型就开始漏指令、混淆轮次。我们不是在省 token， 是在保住注意力预算。

05Fast Path、降级和输出契约

Agent 不是越多越好。这三件事决定了这套东西在真实用户手里会不会崩：什么时候不用模型， 出错时给什么，以及客户端到底能收到什么。

Fast Path：有时不用模型

新会话、没有历史、查询精确命中歌名/歌手时，直接查库返回，跳过模型循环； Run 只做收尾和写状态。如果用户点名了歌手，还要核对歌手是否一致—— “Coldplay 的 Yellow”不能命中别人的 Yellow。

_maybe_fast() · 仅第一轮

Degraded：失败也要有结果

超时、token 用尽、工具连续失败、finish 被拒、步数用尽——每条路径都返回 degraded{reasons, at_step, partial}。有候选就给候选，没有就给一句能看懂的话。

_degraded() · 客户端加“结果可能不完整”

Output：四种类型，一个 trace

正常路径的 songs 由 finish 产生；Fast Path 和 degraded 是两条受控例外。 clarify 写入 pending；refusal 用于空结果/被拒； text 用于没有工具调用的直接回答（追问、寒暄、说明）。 trace 记录每一步，评测和排查都看它。

type + songs + message + degraded + trace

一次请求的真实路径

HarmonyOS AiSearch.ets —SSE→ Koa JWT · 转发 · 150s · 断开即中止 —fetch→ Agent uvicorn · status / result —tools→ MySQL + bge-m3 索引

Agent 循环完全不知道 HTTP 的存在：它只接收 query / session_id / user_id / turn_id， 通过 on_event 往外吐进度。Koa 负责鉴权、超时和客户端断开；客户端负责把 status 和 result 变成气泡。三层各自只做一件事。

06收束

Agent 的全部魔法，是把“下一步做什么”从代码里搬到模型里； 其余四件事——工具、规则、边界、上下文——都是为了让这次搬家不至于失控。
