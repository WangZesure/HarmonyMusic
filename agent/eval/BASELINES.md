# 阶段 3.0 评测集与基线成绩（dev，100 条）

> 生成 2026-10-12。评测集 `golden_dev.jsonl` / `golden_test.jsonl`（各 100 条，6 类）、
> `intent_labels.jsonl`（50 条解析标注）、复核表 `REVIEW.md`（200 条，自动标记 3 条可疑）。
> 运行：`python -m agent.eval.run_eval --file golden_dev.jsonl --methods b0,b1,b2,b3`

## 基线成绩表（k=5）

| 类型 / 指标 | B0 直接猜 | B1 整库入 prompt | B2 单次向量 | B3 原 LIKE |
|---|---|---|---|---|
| 指定歌曲 Hit@1 | 0.867 | **1.000** | **1.000** | 0.000 |
| 描述找歌 Hit@5 | 0.050 | 0.900 | **0.900** | 0.000 |
| 歌词片段 Hit@5 | 0.000 | 0.240 | **0.440** | 0.000 |
| 氛围 nDCG@5 | 0.039 | 0.337 | **0.896** | 0.000 |
| 硬约束满足率@5 | 1.0* | 0.733 | 0.653 | 1.0* |
| 曲库没有·拒答率 | 1.0 | 0.0 | 0.0 | 1.0 |

\* B0/B3 的约束满足率高是假象：它们往往只返回 0–1 首，分母小。

## 结论

- **最强基线是 B2（单次向量检索）**，不是 B1。B1 除了“指定歌曲”满分，其余全面不如 B2，
  而且 prompt 塞 500 首（约 3 万 token/次）很贵 —— 这本身就说明“检索”胜过“塞进上下文”。
- Agent 必须**同时赢 B1 和 B2**：在 B2 已经很弱的**歌词(0.44)**和**硬约束(0.65)**上是主要提升空间，
  描述(0.90)/氛围(0.896) 要保住不退化。
- 曲库没有时，只有 B0/B3 会“拒答”（其实是因为搜不到命中），B1/B2 都会硬凑 —— Agent 需靠拒答逻辑做到 ≥0.9。
