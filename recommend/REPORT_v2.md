# 推荐系统 v2：内容双塔（实验留档）

> 2026-11-11。替代 `recommend/src/` 下基于 TF 的 ID 双塔（v1）。
> 本文档记录**为什么这么设计、怎么评测、结果如何**，包括没跑赢的基线。

---

## 1. 为什么要重做

v1 的问题是**结构性的**，不是训练不够：

| 问题 | 具体表现 |
|---|---|
| **曲库对不上** | 合成数据是 `100 用户 × 10 首歌`，那 10 首是**旧版 demo 曲库**的 ID，和现在 500 首的 Jamendo ID 是两个宇宙 |
| **没有可学的信号** | 用户和歌曲是随机配对的，模型学到的最好策略就是输出先验 |
| **冷启动无解** | 用户和歌曲都是 ID embedding，新歌/新用户永远学不到 |
| **与向量底座脱节** | bge-m3 的 500×1024 索引就在盘上，推荐系统完全没用 |
| **评测无意义** | 只在随机负样本上算 accuracy/precision/recall |

---

## 2. 数据设计（方案 ①A）

### 2.1 生成逻辑

`recsys/data.py · generate_synthetic_plays`

1. **用户口味**：每个用户从**真实标签分布**里抽一个偏好档案
   （1–3 个流派、1–3 个情绪、1–2 个场景）。抽样权重是 `频次^0.75`——
   压一下头部，让长尾标签也有机会出现。
2. **每次播放**：
   - 以 `EXPLORE_RATE = 0.25` 的概率**探索**（全库随机），否则在
     **口味内候选池**（匹配度排序前 40%）里抽；
   - 同一用户不重复听同一首（避免留一法歧义）。
3. **完成率**：`completion = base + 0.45 × match + N(0, 0.08)`，
   其中 `base = 0.15`（探索）/ `0.55`（口味内），`match` 是偏好标签被满足的比例。
4. **is_liked**：`completion > 0.85 且 match ≥ 0.4`。

### 2.2 规模

| 项 | 值 |
|---|---|
| 合成用户 | 200（ID 从 `100000` 起，契约 C1） |
| 每人播放 | 15 条 |
| 总播放 | 3000 条，`source='synthetic'` |
| 完成率均值 | 0.598 |
| is_liked | 206 条（6.9%） |

> **真实播放记录不受影响**：写入前只删 `source='synthetic' AND user_id >= 100000` 的行。

### 2.3 为什么这样生成

旧数据"随机用户听随机歌"，**没有可学的结构**，任何模型都会退化成先验。
新数据把"用户口味 → 歌的标签匹配度 → 完成率"这条因果链显式建出来，
模型才有东西可学；同时保留 25% 探索率，避免数据过于干净（真实用户会点错）。

## 3. 模型（方案 ②A）：内容双塔

`recsys/model.py`

```
歌曲塔： bge-m3 向量(1024, 冻结) → Linear(256) → ReLU → Dropout → Linear(64) → L2归一化
用户塔： 历史向量(1024)          → Linear(256) → ReLU → Dropout → Linear(64) → L2归一化
打分：   scale × cos(user_vec, song_vec)，scale=5.0，BCEWithLogitsLoss
```

**关键设计**：

| 选择 | 理由 |
|---|---|
| 歌曲塔吃 **bge-m3 向量**而非 ID embedding | 新歌入库就有向量（来自文本卡片），冷启动天然可解；且直接复用阶段 1 建好的 `songs_v1` 索引 |
| 用户塔吃 **历史歌曲向量的加权平均** | 用户也活在同一个内容空间里，新用户听几首就能被服务；权重是**完成率**——听完的歌比 10 秒跳过的歌更能代表口味 |
| 两端都 L2 归一化后点积 | 等价余弦，分数范围可控，避免向量范数主导排序 |
| 固定 scale=5.0 | 余弦 ∈ [-1,1]，直接当 logit 太窄，乘 5 后 BCE 的梯度更健康 |

**用户表示用完成率加权而不是简单平均**，是实测出来的：简单平均把 14–20 首歌
糊成一个点，不再像其中任何一首，留一法 Hit@50 只有 0.145；改成加权后升到 0.315。

## 4. 训练配置

| 项 | 值 |
|---|---|
| 样本 | 10209 条（正 1940 / 负 8269） |
| 正样本 | 完成率 ≥ 0.6 的播放 |
| 负样本 | ① 完成率 ≤ 0.3 的播放（用户主动跳过）② 每正样本采 4 首**该用户没听过的歌** |
| 优化器 | Adam，lr 1e-3 |
| batch / epochs | 256 / 60 |
| seed | 20261111 |
| loss | 0.5063 → 0.3751 |

**训练时防泄漏**：计算某条正样本的用户向量时，**排除该样本自己的歌**，
只用该用户的其他播放。

## 5. 评测（方案 ③）

`recsys/evaluate.py`，两个协议，回答两个不同的问题。

### 5.1 协议一：留一法（严格）

每个用户**最后一次播放**留出，其余作为历史，在 500 首里排序，看留出歌落在第几。

| 方法 | Hit@10 | Hit@20 | Hit@50 | NDCG@10 | MRR |
|---|---|---|---|---|---|
| **model** | 0.0550 | 0.1100 | **0.3150** | 0.0269 | 0.0343 |
| tag-match | **0.0650** | 0.1100 | 0.1700 | **0.0312** | 0.0315 |
| popularity | 0.0450 | 0.0650 | 0.1800 | 0.0199 | 0.0226 |
| random | 0.0050 | 0.0300 | 0.1000 | 0.0018 | 0.0093 |

### 5.2 协议二：口味级

用生成时的**真实偏好**算出相关集合（匹配度 ≥ 0.4，平均 103.7 首/人），
衡量模型有没有把用户口味内的歌排上来。

| 方法 | Recall@10 | Precision@10 | NDCG@10 | NDCG@20 |
|---|---|---|---|---|
| model | 0.0381 | 0.3695 | 0.3664 | 0.3664 |
| tag-match | **0.0591** | **0.5495** | **0.5555** | **0.5322** |
| popularity | 0.0290 | 0.3235 | 0.3337 | 0.3158 |
| random | 0.0194 | 0.1954 | 0.1995 | 0.2003 |

### 5.3 怎么读这张表（诚实结论）

**模型赢的地方**：
- 两个协议下都**明显优于 popularity 和 random**（口味级 NDCG@10：0.366 vs 0.334 / 0.200）
- **留一法 Hit@50 是 tag-match 的 1.85 倍**（0.315 vs 0.170）——说明模型的候选池更"宽"，
  能把相关歌整体往前推

**模型没赢的地方**：
- **tag-match 在口味级指标上领先**（0.556 vs 0.366）
- **但这是指标本身的循环性**：口味级相关集就是**按标签重叠定义**的，而 tag-match
  又是从历史里数最高频标签反推偏好——它等于直接优化这个指标，接近 oracle。
  这个数字应当读作"标签启发式能到达的上界"，而不是"模型不如启发式"。

**一句话**：在**标签驱动**的合成数据上，标签启发式占结构性便宜；模型的价值在于
（a）留一法上的候选覆盖更好，（b）不依赖标签也能工作——而后者这条合成数据证明不了，
需要真实数据。

> 这个结论没有粉饰：如果面试被问"你的模型比基线强多少"，诚实的回答是
> "比热门和随机强 10%–80%，但在标签定义的指标上打不过标签启发式，因为数据本身是标签生成的"。

## 6. 线上集成

```
Koa /getRecommendSongs
   └─ exec("$RECOMMEND_PYTHON scripts/api/simple_recommend.py <userId> <count>")
        └─ recsys.serve.recommend()
             ├─ 有播放记录 → 内容双塔
             └─ 无播放记录 → 热门兜底（algorithm="popularity"）
```

**响应里的 `meta.algorithm` 会明确写 `two-tower-v2` 还是 `popularity`**，
不会把兜底伪装成个性化。

**解释器**：推荐脚本需要 torch，系统 python 没有。通过 `.env` 的
`RECOMMEND_PYTHON` 指定（本机为 `D:\apps\tools\Conda\python.exe`）。

实测：

| userId | 情况 | algorithm |
|---|---|---|
| 2（user1，4 条真实播放） | 有个性化 | `two-tower-v2` |
| 100000（合成用户，15 条） | 有个性化 | `two-tower-v2` |
| 999（无记录） | 冷启动 | `popularity` |

---

## 7. 局限

1. **评测数据是自己生成的**。合成数据的分布决定了指标上限，不能等同于真实效果。
2. **口味级指标与生成过程同源**（都是标签重叠），存在循环性，已在 §5.3 说明。
3. **用户塔只用了"听过的歌"，没用时间衰减**。真实场景里上周和去年的播放权重应该不同。
4. **没有做在线 A/B**。`user_plays` 现在有 4 条真实记录，量还不足以验证。
5. **v1 的 TF 代码仍在 `recommend/src/`**，未删除，以免影响历史文档引用；新链路不依赖它。
6. **`recommend/models/` 仍是旧路径**，新模型在 `recommend/artifacts/`。

## 8. 复现

```bash
cd recommend
PY="D:/apps/tools/Conda/python.exe"

$PY -m recsys.generate    # 生成 200 用户 × 15 条播放，写入 user_plays
$PY -m recsys.train       # 训练，产出 artifacts/two_tower_v2.pt + meta_v2.json
$PY -m recsys.evaluate    # 留一法 + 口味级评测，产出 artifacts/eval_v2.json

# 单用户推理
$PY scripts/api/simple_recommend.py 100000 6
```

环境变量可覆盖：`REC_SEED` / `REC_N_USERS` / `REC_PLAYS_PER_USER` /
`REC_EXPLORE_RATE` / `REC_EPOCHS`。

**依赖**：torch、numpy、scikit-learn、pymysql（本机 `D:\apps\tools\Conda` 已具备）。
